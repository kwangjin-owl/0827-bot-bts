요약 — 네 기둥 · 흐름만

손님 / 말 / 판단 / 기록 네 기둥. 구현 상세는 뺐습니다.

sequenceDiagram
    autonumber
    actor U as 손님
    participant I as agent UI<br/>말
    participant L as agent Logic<br/>판단
    participant D as agent Data<br/>기록

    Note over U,D: [단계 1] 장소 접수 - 같은 칸을 두 방식으로
    alt 폼으로 예약
        U->>I: 갈래와 조건 입력
        I->>L: 입력 전달
        L->>D: 후보 조회
        D-->>L: 헬스장 켜면 71곳 → 19곳
        L-->>I: 후보 목록
        U->>I: 장소 선택
        L->>D: 주소/연락처/평점 조회
        D-->>I: 자동 칸 반영
    else 챗봇으로 예약
        U->>I: 자연어 발화
        I->>L: 발화 전달
        L->>D: 최근 2턴 창 조회
        D-->>L: 창 안만 반환(밖은 안 넘김)
        L->>D: 메모판 조회(넘기기를 켰을 때만)
        D-->>L: 창 밖 칸까지 반환 - 이때는 밀림이 사라짐
        L->>D: 장소사전 대조
        D-->>L: 창과 무관하게 항상 반환
        L->>D: 이번 턴 기록
        L-->>I: 부족한 칸 1개 질문 생성
        I->>U: 들은 값 되짚기 + 한 칸 질문
    end
    Note over L,D: 창은 밀린다 · 사전은 안 밀린다 · 메모판을 넘기면 창 밖 칸도 본다

    Note over U,D: [단계 2] 두 도메인이 이어지는 자리 - 장소 이름 → 택시 칸
    Note over L,D: 실데이터 - 출발지 47 / 도착지 24 / 연결 안 함 29 → 자동 이월 금지
    L-->>I: 어느 칸에 넣을지 질문 생성
    I->>U: 타세요, 아니면 가세요
    U->>I: 응답
    I->>L: 응답 전달
    L->>L: 타는 곳/내리는 곳 확정

    Note over U,D: [단계 3] 배차 및 저장
    U->>I: 출발 시간과 택시 종류 입력
    I->>L: 배차 요청
    L->>L: 기사 배정 및 연락처 발급
    L->>D: booking 저장(폼·챗봇 공용 표)
    D-->>L: 예약번호와 기사 연락처
    L-->>I: 완료 안내 생성
    I->>U: 예약번호 · 경로 · 기사 연락처

손님은 말만 하고, 판단은 가운데서, 기록은 오른쪽에서 일어난다. 폼과 챗봇은 말하는 방식만 다를 뿐 같은 판단과 같은 기록을 쓴다. 갈리는 지점은 단계 2 하나뿐이고, 거기서 봇은 자동으로 정하지 않고 한 번 묻는다. 기록 기둥 안에서 창은 밀리고 메모판은 안 밀린다.

같은 네 기둥에 로그인과 슬롯 정의 적재, 저장까지 넣었습니다.

  
sequenceDiagram
    autonumber
    actor U as 손님
    participant I as agent UI<br/>말 · 폼과 챗봇
    participant L as agent Logic<br/>판단 · 슬롯과 이월
    participant D as agent Data<br/>기록 · 창 · 메모판 · 사전 · Supabase

    Note over U,D: [단계 0] 로그인과 슬롯 정의 적재
    U->>I: 구글 로그인 클릭
    I->>D: Supabase Auth 로 위임(우리는 비밀번호를 받지 않음)
    D-->>I: 세션과 user_id 반환
    Note over D: settings.py → make_config.py 또는 build.js → config.js<br/>ASK_SLOTS 9칸 · DOMAIN_SLOTS · FILTERS · ASK_STYLE · HISTORY_TURNS
    D-->>I: 묻는 칸 목록과 질문 문구 제공
    D-->>L: 항목별 후보값 제공(갈래 3 · 지역 5 · 가격대 3 · 택시 4)

    Note over U,D: [단계 1] 장소 접수 - 같은 아홉 칸을 두 방식으로
    alt 폼으로 예약(아홉 칸이 한 화면)
        U->>I: 갈래 선택(관광/숙소/식당)
        I->>L: 갈래별 칸 구성 요청
        L->>D: 도메인 슬롯 조회
        D-->>L: 관광 8칸 · 숙소/식당 9칸
        L-->>I: 칸 재구성 반영(관광에는 가격대가 없음)
        U->>I: 조건 입력(종류/지역/가격대/옵션)
        I->>L: 조건 전달
        L->>D: 후보 조회(조건 AND 결합)
        D-->>L: 헬스장 켜면 숙소 71곳 → 19곳
        L-->>I: 후보 목록 제공
        U->>I: 장소 선택
        L->>D: 주소/연락처/평점 조회(AUTO_SLOTS)
        D-->>I: 자동 칸 반영
    else 챗봇으로 예약(한 칸씩 주고받기)
        U->>I: 자연어 발화(예 - 헬스장 있는 숙소요)
        I->>L: 발화 전달
        L->>D: 최근 HISTORY_TURNS 턴 창 조회
        D-->>L: 창 안 발화만 반환(밖으로 나간 턴은 안 넘김)
        L->>D: 메모판 조회(넘기기를 켰을 때만)
        D-->>L: 창 밖 칸까지 반환 - 켜면 밀림이 사라짐
        L->>L: Gemini 추출 요청(api/extract.js) - 실패 시 규칙으로 대체
        L->>L: 조건만은 LLM 이 성공해도 규칙으로 한 번 더 훑음
        L->>D: 장소사전 대조(갈래/종류/지역 보강)
        D-->>L: 정규화 값 반환(창과 무관하게 항상 조회 가능)
        L->>D: 이번 턴 기록(다음 창에 실림)
        L-->>I: 부족한 칸 1개 질문 생성
        I->>U: 들은 값 되짚기 + 한 칸 질문
    end
    Note over L,D: 창은 밀린다 · 사전은 안 밀린다 · 메모판을 넘기면 창 밖 칸도 본다<br/>창 밖으로 나간 칸은 지운 글씨에 잊음으로 표시

    L->>D: 후보 수 확인
    D-->>L: 0곳이면 조건을 하나씩 빼 보고 몇 곳이 되는지 셈
    L-->>I: 무엇을 풀지 제시(가격대를 빼면 3곳 · 지역을 빼면 2곳)
    I->>U: 이름 대신 되돌릴 길을 묻는다

    Note over U,D: [단계 2] 두 도메인이 이어지는 단 하나의 자리 - 장소 이름 → 택시 칸
    Note over L,D: 실데이터 - 출발지 47 / 도착지 24 / 연결 안 함 29 → 자동 이월 금지
    alt 폼
        U->>I: 장소와 같게 체크(타는 곳 또는 내리는 곳)
        I->>L: 이월 지정 전달
        L->>L: 이월 칸 고정(장소를 바꾸면 그 칸만 따라감)
    else 챗봇
        L-->>I: 이월 질문 생성(어느 칸에 넣을지)
        I->>U: 호텔 파크에서 타세요, 아니면 호텔 파크로 가세요
        U->>I: 응답
        I->>L: 응답 전달
        L->>L: 타는 곳/내리는 곳 확정(carry 처리)
        L->>L: 장소 변경 시 옛 이름 잔존 검사 후 재확인
    end

    Note over U,D: [단계 3] 택시 연계 배차 및 데이터 갱신
    U->>I: 출발지/시간/택시 종류 입력 후 배차 요청
    I->>L: 배차 요청 전달
    L->>L: 빈 칸 검사(빈 칸이면 그 칸의 질문을 그대로 노출)
    L->>L: 기사 배정 및 연락처 자동 발급(AUTO_SLOTS)
    rect rgb(238, 242, 250)
        Note over D: [기록 - 손님에게 안 보이는 처리]
        L->>D: booking 저장(폼·챗봇 공용 표 · user_id 포함)
        L->>D: booking_change 기록(사람이 고친 칸과 따라 바뀐 칸 구분)
        D-->>D: RLS 검사(로그인하면 내 것만 · 익명은 익명끼리)
    end
    D-->>L: 예약번호 TX-0007 · 기사 연락처
    L-->>I: 완료 안내 생성
    I->>U: 예약번호 · 경로 · 출발 시간 · 기사 연락처
  

  
기록 기둥 안에 네 가지가 같이 산다. 대화 창은 밀리고, 메모판과 장소사전과 슬롯 정의는 안 밀리고, Supabase 는 완료된 것만 남긴다. 창만 넘기면 도보 조건이 밀려 61곳이 되고, 메모판까지 넘기면 3곳으로 좁혀진다. 같은 모델 같은 대화인데 무엇을 넘겨주느냐로 갈린다. 로그인하면 그 사람 것만 보이고, 그 경계는 화면이 아니라 RLS 정책이 만든다.
